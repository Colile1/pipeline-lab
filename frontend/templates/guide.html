What this is

Pipeline Lab measures how much ordinary data-preparation choices change how well a machine learning model predicts. It runs the experiments, stores everything about them, and shows what the results mean.

You do not need a background in machine learning to use this page. Each section starts in plain language, and the grey expandable blocks add the technical detail underneath if you want it.

The idea in one minute

Before a model ever sees data, a person makes five decisions about how to prepare it:

  1. Scaling. Put columns on a comparable footing. A salary column running to six figures and an age column running to two are not naturally comparable, and some models are badly misled by that.
  2. Missing values. Decide what to do about blanks: drop those rows, fill them with the average, or estimate them from similar rows.
  3. Encoding. Turn words into numbers, because models do arithmetic. "Red, green, blue" has to become numbers without accidentally implying that blue is greater than red.
  4. Feature selection. Decide which columns to keep. More is not always better; irrelevant columns can drown the signal.
  5. Tuning. Search for the model's own settings rather than accepting the defaults.

These are usually settled by habit or by whatever the software does by default. This project asks a simple question about each one: does it actually change the answer, and is it worth what it costs?

Why this question is harder than it sounds

If you change two things at once and the result improves, you cannot tell which change did it. So every experiment here varies exactly one of the five decisions and holds the other four at a fixed baseline. That design is called one-factor-at-a-time, or OFAT.

It has a known limitation, stated plainly because it affects how the results should be read: OFAT cannot detect interactions, where two choices only matter in combination. Testing every combination of five choices would take tens of thousands of runs, which is not feasible on one machine. The trade is deliberate and recorded.

A second trap is subtler. If you prepare the data using information from the rows you later test on, the model looks better than it is. This is called leakage. Every transformation here is fitted inside the training portion only, and the engine has instrumentation that records which rows each step saw, with tests that deliberately build a leaky pipeline to confirm the check actually catches one.

The pages, and when to use each

Dashboard

Start here. It shows how many experiments have been run, how much computing time they used, and a list of every experiment with a link into its results. If a sweep is running right now, the badge at the top says so and the page keeps itself up to date.

Findings

The most important page. It takes one experiment and says whether the differences in it are real, using the same statistical tests as the written research. It will tell you three different things, and the difference between them matters:

  • A real difference - the evidence supports it.
  • No difference found - the options performed about the same. This is a genuine result, not a failure.
  • Not enough datasets to decide - the test arithmetically could not have found anything. This is not the same as "no difference", and the page says so in red when it happens.

Explorer

For your own questions. Plot any recorded field against any other, split it by model or dataset, and download the underlying rows as a spreadsheet. The ready-made buttons answer the four most common questions in one click.

Compose, Network, Trends

Compose is where you build and launch a new experiment by dragging options into columns; it prices the job before it starts, because a sweep that looks small can be thousands of model fits. Network draws the pipeline as a graph. Trends is a lighter-weight view of a single launched run.

Reading a result without being misled

What a p-value does and does not tell you

A p-value is the chance of seeing a pattern at least this strong if the options were really identical. Small means "hard to explain as luck". By convention, below 0.05 is treated as evidence.

It does not tell you how big the difference is. A tiny, useless difference can be statistically significant if you measure it enough times, and a large, valuable difference can fail to reach significance if you have few datasets. That is why every p-value on these pages is shown next to the size of the change and the number of datasets it helped.

Why "not significant" sometimes means "we could not tell"

The test used here works on ranks and is discrete: with a small number of datasets there is a hard floor below which its p-value cannot go, no matter how large the effect.

With 6 datasets that floor is 0.031, and because several options are compared at once the bar moves to roughly 0.017. So a method that won on all six datasets still could not be declared significant. That is a limit of the arithmetic, not evidence that the method does not work.

This actually happened in this project: robust scaling improved the error on six datasets out of six and could not be reported as a finding. The Findings page now detects this situation and says, in red, how many datasets would be needed.

Why a skipped run is a good sign

Some runs appear as "skipped" with a reason attached. One real example: a dataset where a fifth of the values were missing, and the baseline rule was to drop any row containing a blank. That left 7 usable rows out of 368 - too few to split into 10 groups for testing.

The engine refused and recorded why, rather than producing a number that would have looked fine in a table and meant nothing. Skips are kept in the record and counted on the Dashboard.

Averages hide things. Look at the spread

A method that helps enormously on half the datasets and hurts on the other half can have the same average as one that does nothing anywhere. The two are not the same recommendation.

On the Explorer, set "Compare across" to dataset to see each dataset separately. On Findings, the "datasets it helped" bar shows the win and loss count directly, which is usually more honest than the average.

A real example from this project: scaling made almost no difference on a dataset whose columns were already on the same scale, and a 42% difference on one whose columns spanned a range of 170,000 to 1. Whether preparation matters depends on the data you have, which is exactly the kind of finding an average alone would bury.

Where the numbers live

Every run writes one row to a single database file, with 86 fields recording what was run, what it scored, how long it took, how much memory it used, and the exact machine and library versions that produced it. Nothing on these pages is stored separately or cached: the website reads that file directly, read-only.

That is why an experiment launched from the command line shows up here with no extra step, and why these pages cannot corrupt a run that is in progress.

Getting the data out

The Explorer has a Download CSV button that exports every field of every row for the selected experiment, so the numbers can be checked independently in a spreadsheet or statistics package.

From code, the record is an ordinary SQLite database with one table named runs, so any SQL tool can read it. The Dashboard shows its full path.

Why so many fields per run

Because the interesting questions are often not the ones you thought to ask. Storing the machine, the memory, the timing and every library version means a trend can be investigated later without re-running anything, and means a surprising result can be checked against the conditions that produced it.

It also makes the work reproducible. A run records its random seed and the exact fold split it used, so the same experiment can be repeated and checked.

A short glossary

Model
The algorithm that learns the pattern and makes predictions.
Feature
One column of input data. Age, salary and city are features.
Accuracy
How often the model is right, as a fraction. 0.95 means right 95 times out of 100.
Macro-F1
A score that treats small groups as just as important as large ones. Useful when one answer is far more common than another, where plain accuracy can look good while the model ignores the rare case.
RMSE
For predicting a number rather than a category: how far predictions land from the truth on average. Lower is better.
Cross-validation
Splitting the data into ten parts and testing ten times, each time holding out a different part. Gives a more trustworthy score than a single split, and shows how much the score wobbles.
Baseline
The option everything else is compared against, usually "do nothing". Having a fixed reference is what makes a comparison meaningful.
Leakage
When information from the test data sneaks into preparation, making results look better than they really are. The main thing this engine is built to prevent and to prove it prevents.
Sweep
One experiment: every combination of one varied decision across the chosen datasets and models.
