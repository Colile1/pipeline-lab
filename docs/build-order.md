# Build order

Build and commit one step at a time, in order. ⚠ marks a
correctness-critical step (see the model policy in the design notes).

| # | Step | Verification |
|---|---|---|
| 1 | Project scaffolding: `backend/app/main.py` (FastAPI app, mounts static frontend), pin `requirements.txt` (fastapi, uvicorn, pyyaml, pandas, python-multipart) | `uvicorn app.main:app` starts, root route returns the shell page |
| 2 | Azure-portal frontend shell: `frontend/templates/base.html`, `frontend/static/css/azure-theme.css` — top app bar, left nav rail, card-tile layout, Azure blue (#0078D4) palette, light theme | Shell page renders in browser with nav + empty content area, matches Azure portal visual pattern |
| 3 | `backend/app/engines/base.py` (Engine protocol: name, root path, config schema, fixed-design lists) + `backend/app/engines/prepfx.py` + `backend/app/engines/b2.py` (concrete paths + fixed lists read from each engine's real config examples) | Unit test: each engine adapter reports the correct fixed technique/model lists matching that engine's design notes |
| 4 ⚠ | `backend/app/core/config_builder.py` — pure function(s): wizard form dict → validated YAML matching the target engine's schema; rejects invalid factor/technique/model/missingness combos | Unit tests: valid B1 scaling config, valid B2 imputation config (with rates/mechanisms), and at least 2 rejected invalid combos, all byte-for-byte/structurally match a real example config from that engine's `configs/` folder |
| 5 | `backend/app/api/datasets.py` — GET list of each engine's registered datasets (read B2 `catalogue.csv`, read prepfx dataset registry) | `GET /api/datasets?engine=b2` returns the real catalogue rows as JSON |
| 6 ⚠ | `backend/app/uploads/validate.py` + `backend/app/uploads/characterise.py` + `POST /api/datasets/upload` — validate uploaded CSV (has target column, no all-NaN columns, inferable task type), compute catalogue characteristics (n_rows, n_features, missing_pct, imbalance_ratio or var_ratio_log10/mean_abs_corr as applicable), record it in the target engine's own user-dataset file (read by that engine's `registry.py` hook; the registered design and B2's generated catalogue.csv are never written) and cache the CSV where that engine expects it. Characteristics are computed by the engine's own code under its own interpreter (`uploads/register.py` + `engines/<engine>/register_dataset.py`) | Upload a real sample CSV via the API, confirm a new row appears in the engine's user-dataset file with correct computed values, and the engine's own loader can read it back |
| 7 | `backend/app/core/runner.py` — launches `python run_experiment.py --config <path>` as a detached background subprocess per engine, returns a run-id, tracks process handle + log file | Launch a smoke config via the module directly, confirm the subprocess runs to completion and its stdout is captured to a log file keyed by run-id |
| 8 ⚠ | `backend/app/core/run_status.py` — parses a run's log + checks whether expected output files exist; produces the post-run validation summary (config used, folds expected vs completed, errors/exceptions seen in log, achieved missingness rate vs requested by reading the engine's own output, if available) | Run a real smoke config end-to-end, confirm the parsed summary correctly reports success, and confirm it correctly reports failure/missing folds when a config is deliberately broken |
| 9 | `backend/app/api/experiments.py` — POST to build+validate a config (calls step 4), GET to list available factor/technique/model choices per engine (calls step 3) | API round-trip: POST a wizard payload, get back the generated YAML path; GET choices matches the engine's fixed lists |
| 10 | `backend/app/api/runs.py` — POST to launch a run (calls step 7), GET run status/validation summary (calls step 8), GET live log tail | Launch a run via the API, poll status until complete, confirm the validation summary matches a direct read of the engine's own output |
| 11 | `backend/app/api/results.py` + `frontend` results page — reads the engine's real summary/verdict CSVs for a completed run and renders as sortable tables + simple charts | Load a real past B1 and B2 summary CSV through the API and confirm the rendered table values match the raw CSV exactly |
| 12 | Frontend wizard pages: Datasets, New Experiment, Runs, Results — wire to the APIs above, Azure card-tile styling throughout | Manual walkthrough in browser: upload CSV → configure → run smoke config → see validation summary → see results, for both engines |
| 13 | Smoke run end-to-end + README quick-start verification | Fresh clone, `pip install -r requirements.txt`, `uvicorn app.main:app`, full walkthrough from step 12 succeeds with no manual file edits |
